# 067: HTTP/3, off by default

Status: done (2026-10-24). Built on both Linux loops and macOS's kqueue, over
goose-tls's task 008, checked against two clients of their own QUIC, validated in
Plod's entry, measured on Linux, released in `v0.5.10`, and tuned in `v0.5.11`. Round 3
adds path MTU probing, for datagrams of 1,452 bytes, to be released; the board's numbers
for the tuned entry are left ("Round 3").

Plod's HttpArena entry (Plod's task 047) wants baseline-h3 and static-h3, the h3 board's
two profiles, which only native QUIC enters. HTTP/3 costs more CPU per request than h2,
so goose-http serves it only where a program asks, and the HTTP/1.1, h2c, and TLS paths
must not get slower or bigger for programs that don't.

## Decisions

Taken 2026-10-24, recorded in [decisions](../docs/decisions.md#http3-is-an-optional-module-over-quic-in-goose):

1. QUIC and HTTP/3 are written in Goose, in the optional module `http.h3`, over
   goose-tls's QUIC mode for the handshake and packet protection; not ngtcp2 and
   nghttp3.
2. `Listener.h3` turns it on per listener, beside `tls`; not ALPN alone, which would
   open UDP on every TLS listener of a context, 8081 too in HttpArena's entries.

zix, agensio, and nginx run their own QUIC. Aegon's entry builds `e649022`, before its

zix's rate comes in part from what it leaves out (read at `881ccea`, 2026-10-24): its
responses carry `:status` alone, a small response is never sent again if lost, the
handshake isn't sent again, the client's Finished isn't checked, there's no
amplification limit or key update, and a CRYPTO offset from the wire is written
unchecked. Aegon leaves out less: it scans every connection's timers each 10 ms,
creates state for any Initial, and drops sends when the socket's buffer is full. This
task's QUIC does each of those, so its numbers compare to a server on the internet.

## As built

How it works is in [architecture](../docs/architecture.md#http3), and its API in
[api](../docs/api.md#http3).

- One UDP socket per worker per h3 listener, with `SO_REUSEPORT`, armed for readiness
  with `net_arm` on epoll and io_uring; `recvmmsg` up to 32 datagrams a call, and
  `sendmmsg` with GSO runs (`shim/net.c`). macOS: one datagram a call.
- A connection's ID is 8 random bytes; its datagrams go through goose-tls, a packet a
  call. Datagrams of at most 1,200 bytes, ACK first, then owed frames, CRYPTO, and the
  streams' data in turn, so many small responses share a packet.
- RFC 9002's loss detection, PTO, and NewReno with persistent congestion; the
  anti-amplification limit; the handshake sent again on loss; key updates followed,
  with the previous phase kept for three PTOs; the AEAD limits; 62-bit packet numbers;
  idle timeout; closing and draining.
- HTTP/3: SETTINGS (QPACK capacity 0, no blocked streams), GOAWAY on a stop, the
  client's control and QPACK streams checked, request streams to the handler as h2's
  are, and requests that break the rules reset with H3_MESSAGE_ERROR.
- Not built: `later` on an h3 exchange (it gets TIMEOUT with NO_ROOM at once), 0-RTT,
  connection migration (`disable_active_migration`), Retry, stateless reset, ECN,
  pacing, BPF steering, Windows, and the emulated ring.

## Tuning

### Round 1 (2026-10-24)

On Tiamat, natively in WSL: Plod's entry built with gcc at Goose's default `-O2` from
the local checkouts, 4 workers on CPUs 0-3; h2load 1.69 with ngtcp2 (HttpArena's
h2load-h3 image's, copied out) on CPUs 4-15, 12 threads, 64 connections × 64 streams,
5 s, over loopback.
static-h3 sends HttpArena's 20 URIs with its `Accept-Encoding`. Instructions and cycles
are the server's user ones (perf stat), per request. Medians of 3 rounds, alternating
the builds:

| | Before | After | Change |
|---|---:|---:|---:|
| baseline-h3, requests a second | 1.24 M | 1.52 M | +23% |
| Instructions, cycles a request | 21,340, 12,620 | 13,370, 9,860 | −37%, −22% |
| static-h3, requests a second | 76.7 K | 105.8 K | +38% |
| Instructions, cycles a request | 432 K, 154 K | 145 K, 90 K | −67%, −42% |
| static-h3's RSS | 187 MiB | 206 MiB | +19 MiB |

Each step was measured against the one before it, over 2 rounds:

1. **The static table found by name** (`qpack_find`): a hash of names and a chain of
   each name's entries, as HPACK's table has, where it scanned all 99 entries for each
   field. Part of the next step's gain.
2. **The last response head's field section kept** (`h3_head_block`): a route's heads
   repeat within a second, and Huffman coding their values was most of their encoding.
   Steps 1 and 2: −12% instructions on baseline-h3.
3. **A list of the streams made readable** (`H3Conn.ready`), so a connection's turn
   doesn't visit every stream to find them, and one pass, not two, for MORE and the
   streams done: −3% instructions, −7% cycles. The visits were cache misses, a
   545-byte stream each.
4. **A flag for the streams' owed frames** (`H3Conn.owe_streams`), so a packet doesn't
   visit every stream for MAX_STREAM_DATA, STOP_SENDING, and RESET_STREAM: −4%
   instructions.
5. **A list of the streams with bytes to send** (`H3Conn.sending`), which a packet
   serves in turn, where it visited every stream; a stream leaves it once a packet
   finds it has nothing left: −5% to −7% instructions, −4% to −6% cycles.
6. **Copies at memmove's speed** (`net_copy`): Goose's `copy_into` is a byte loop
   under gcc ([findings](../docs/goose-findings.md#copy_into-copies-a-byte-at-a-time),
   [decision](../docs/decisions.md#c-where-goose-blocks-a-measured-cost-until-goose-has-a-way)),
   and it was 44% of static-h3's user instructions: static-h3 +31% requests a second,
   −58% instructions; baseline-h3 +2%. With `run_shift`'s byte loop too: a further −10%
   instructions on static-h3, its rate within the spread.
7. **The sending list compacted only when a stream finished**, not after every packet:
   static-h3 −10% instructions, −3% to −6% cycles.

After each step's batch: `scripts/test-h3.sh` on epoll and io_uring, 13 of 13; the loss
checks of "Checked" (5% loss with 2 ms delay, 20,000 requests; 20% loss, 5,000
requests), all 2xx; and static-h3's files under 5% loss, 10,000 requests, all 2xx. At
the end, `H3=1 scripts/test.sh` passed.

Where static-h3's time goes now: libcrypto's AEAD 26% of the user instructions,
`memmove` 16%, and this package 51%. A body is copied three times on its way out: into
its stream's run, into a packet, and into the send queue.

### Round 2: memory (2026-10-24)

The same setup. static-h3's RSS was the worker's byte pool, `h3bytes`: about 46 MB
each, and it grew with the streams in flight, 39 MiB at 8 streams a connection to 205
MiB at 64. It held about 4,096 whole responses, queued unsent: over TCP the socket's
buffer holds them and the server stops reading, which this transport didn't do.

- **A connection with 64 KB queued unsent takes no new request** (`H3_QUEUED`): one
  waits, readable, until a turn after the queue goes out, as a TCP server's reads wait
  on a full socket. What a server holds is then a connection's queue and what's in
  flight, not every stream's response, and a client can't make it buffer more by
  asking for more at once. Over 2 rounds: static-h3's RSS 206 to 119 MiB, its rate
  +5% (108 K to 113 K); baseline-h3 −1.6%, with 0.4% more instructions, its responses
  too small to fill the queue. At 256 KB, static-h3's RSS was 151 MiB at the same rate.
  What's left is mostly what's sent and not yet acknowledged, which the transport keeps
  for loss and the congestion window bounds.

Tried, and dropped as no gain: freeing an exchange's state once its response ended,
rather than when its stream's bytes are acknowledged (RSS the same: the state held
little), and sizing a response's run once for its HEADERS and DATA (the pool the same
size: it wasn't fragmentation).

Not done:

- **Datagrams of 1,452 bytes**: at most +5% on static-h3 and +3% on baseline-h3 (a
  build with `H3_DATAGRAM` at 1,452, 2 rounds), but more than 1,200 bytes needs path
  MTU discovery (RFC 9000, section 14; RFC 8899) and the peer's
  `max_udp_payload_size`, or a path with a smaller MTU drops every full packet. Done
  in round 3, by probing.
- **BPF steering of `SO_REUSEPORT`**: a new connection's first packets carry an ID
  the client chose at random, so a stateless program steers as randomly as the
  kernel's hash, and 64 connections over 64 workers still leave about a third idle.
  Balancing them needs state, an eBPF map, which needs privileges a container
  doesn't have.
- **Socket buffers**: each UDP socket asks for 4 MB, which HttpArena's `rmem_max` and
  `wmem_max` of 7,500,000 allow.

After it: `scripts/test-h3.sh` on both loops, 13 of 13; the loss checks, all 2xx;
static-h3's files under 5% loss, 20,000 requests, all 2xx. Runs at 20% loss took 1.7 s
to 60 s on either build, by when an unlucky handshake's timer fired.

### Round 3 (2026-10-24)

On Tiamat, natively in WSL, as round 1, but built as the entry's image builds it,
gcc `-O3 -march=native`, from this branch and Plod's `static-files` branch (whose
entry serves `/static/` through goose-http's file cache), with `/data/static`
bind-mounted as in HttpArena's container. 2 rounds, alternating the builds.

**Path MTU probing** (RFC 8899, one step; RFC 9000, section 14). Once its handshake
is confirmed, a connection sends a PING padded to 1,452 bytes, or to the client's
`max_udp_payload_size` if that's smaller, within its congestion window. Acknowledged,
it makes the connection's datagrams that size. A lost probe isn't congestion: it
leaves NewReno and persistent congestion alone, and is sent again, 3 times in all,
then after 600 s (RFC 8899's `PMTU_RAISE_TIMER`). Persistent congestion at the larger
size takes the connection back to 1,200 bytes, as a path that stopped carrying them
(RFC 8899, section 4.3). The probe goes alone, not through the send queue: the socket
sets DF (`IP_PMTUDISC_PROBE`), so on a path with a smaller MTU the kernel refuses it
with `EMSGSIZE`, which would have held the queue, and a GSO run that began with it
would have failed whole with `EINVAL`, which turns GSO off for the worker. macOS's
socket now sets `IP_DONTFRAG` and `IPV6_DONTFRAG` too, not yet run on macOS.

| | Before | Probing | Change |
|---|---:|---:|---:|
| static-h3, requests a second | 129.2 K, 129.7 K | 137.7 K, 129.7 K | +6.6%, 0% |
| User instructions, cycles a request | 140.5 K, 86.3 K | 131.1 K, 80.0 K | −6.7%, −7% |
| baseline-h3, requests a second | 1.590 M, 1.559 M | 1.626 M, 1.607 M | +2.3%, +3.1% |

On loopback, `tcpdump` shows the server's GSO runs as multiples of 1,452 bytes. Over
WSL's `eth0`, whose MTU is 1,280, every probe was refused, no datagram passed 1,200
bytes, and static-h3's files under 5% loss and 2 ms delay took the same time with
probing as without (8.6 s and 8.9 s, against 8.9 s; 20,000 requests, all 2xx). After
it: `scripts/test-h3.sh` on epoll and io_uring, 13 of 13; the loss checks (5% loss with
2 ms delay, 20,000 requests; 20% loss, 5,000 requests), all 2xx.

**The copies of a response body**, into its stream's run, into a packet, and into the
send queue: `memmove` is 12% of static-h3's user instructions at `-O3`, libcrypto's
AEAD 42%, and this package 40%. Laying each datagram out at the send queue's end, in
place of copying it there, would save the third copy, about 4% of the instructions.
Not done: the queue would have to shrink once sent, and Goose's checker refuses a
global that shrinks while the io_uring loop holds the TLS and h3 servers, whose
stored slices could point into it (spec §5.1), as the comment on the transport's
globals says. Doing it means the loop hooks owning the queue and handing it down, with
what the kernel doesn't take kept in a global until the next pass. The copy into a
packet is the AEAD's input, which goose-tls seals in place.

**HTTP/1.1 with h3 on.** The entry built with and without its h3 listener, `-O3`,
baseline's request over plain HTTP/1.1 (wrk, 256 connections), 3 rounds: 4,325 to
4,326 user instructions a request on, 4,303 to 4,307 off, so +20 (0.5%); user cycles
+1.2% to +3.4%; requests a second within the runs' spread (on 327.8 K, 324.4 K,
326.6 K; off 328.2 K, 326.9 K, 316.4 K); peak RSS 16 MiB against 14. The kernel spends
about 32.7 K cycles a request there, so the user's extra 70 are about 0.2% of it. A
profile puts the difference in `ring_loop` (+65 instructions a request) and in what
gcc inlined around it differently (libc's share −165, `answer` and Plod's `on` +50
each), not in the hooks' work, a few instructions a turn. Goose has no way to keep a
function out of line, so it stays as it is; programs without `http.h3` don't pay it.
